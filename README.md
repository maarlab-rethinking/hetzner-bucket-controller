# hetzner-bucket-controller

[![CI](https://github.com/maarlab-rethinking/hetzner-bucket-controller/actions/workflows/ci.yml/badge.svg)](https://github.com/maarlab-rethinking/hetzner-bucket-controller/actions/workflows/ci.yml)

Declarative **Hetzner Object Storage buckets** for Kubernetes. A `Bucket` object describes a bucket —
location, Object Lock, default retention, versioning, lifecycle rules — and the controller creates
it if it is missing and keeps its configuration as declared, correcting drift made outside the
cluster.

Apache-2.0. Maintained by Maarlab Rethinking.

## Why

Backups belong in object storage, and backup buckets need configuration that must not silently
drift: an Object Lock retention that makes them immutable, and lifecycle rules that expire them
after the lock lapses. Creating them with one-off scripts or sync hooks leaves that configuration
unchecked between runs, and hides the one failure that cannot be repaired — a bucket that was
created without Object Lock. This controller turns the bucket into a reconciled resource with
explicit status.

Neither ACK, Crossplane nor COSI works against Hetzner's reduced S3 API;
[ADR-0001](docs/decisions/0001-own-controller.md) says why.

## Install

```console
helm upgrade --install hetzner-bucket-controller charts/hetzner-bucket-controller \
  --namespace object-storage --create-namespace \
  --set 'rbac.secretNamespaces={backup-buckets}'
```

`rbac.secretNamespaces` lists the namespaces that hold `Bucket` objects: the controller may read
Secrets there and nowhere else.

## A bucket

```yaml
apiVersion: objectstorage.maarlab.dev/v1alpha1
kind: Bucket
metadata:
  name: management-backups
  namespace: backup-buckets
spec:
  name: maarlab-management-nbg1-backups
  location: nbg1 # endpoint defaults to https://nbg1.your-objectstorage.com
  credentials:
    name: object-storage-management-backups
  objectLock:
    defaultRetention:
      mode: COMPLIANCE
      days: 30
  lifecycle:
    rules:
      - id: expire-snapshots
        expirationDays: 35
        noncurrentVersionExpirationDays: 5
      - id: drop-delete-markers
        expiredObjectDeleteMarker: true
```

```console
$ kubectl get buckets -n backup-buckets
NAME                 BUCKET                            LOCATION   LOCK         READY   REASON      AGE
management-backups   maarlab-management-nbg1-backups   nbg1       COMPLIANCE   True    Available   2m
```

The Secret `object-storage-management-backups` holds an S3 key pair, keys `access-key` and
`secret-key`; [examples/externalsecret.yaml](examples/externalsecret.yaml) materialises it from
OpenBao.

## The credential chooses the project

Hetzner has no API to create S3 credentials: they are generated by hand in the Hetzner Console, per
project, and give full access to every bucket of that project. The controller only consumes them,
so **the credential decides which Hetzner project a bucket is created in**. It reads the Secret on
every pass, uncached, so a rotated key is picked up without a restart
([ADR-0005](docs/decisions/0005-credentials-read-per-namespace.md)).

## Deleting a Bucket never deletes the bucket

Deleting a `Bucket` object only stops the reconciliation; the bucket and its data stay in Hetzner.
Backups must outlive any Kubernetes object, and with Object Lock the deletion would fail anyway.
There is no finalizer, so a `Bucket` never gets stuck in `Terminating`, and creating the `Bucket`
again adopts the existing bucket
([ADR-0004](docs/decisions/0004-orphan-on-delete-without-finalizer.md)). Retiring a bucket is a
manual procedure, in [operations](docs/operations.md#retiring-a-bucket).

## Only what Hetzner supports

Hetzner implements a subset of S3, and the API models exactly that subset
([ADR-0002](docs/decisions/0002-model-only-what-hetzner-documents.md)). Its constraints are enforced
by the API server rather than discovered on the first reconcile:

- **Object Lock can only be chosen at creation.** The presence of `spec.objectLock` is immutable. A
  bucket that already exists without it is reported with `ObjectLockMissing`, never "fixed": the
  only fix is a new bucket.
- **Bucket names are global** across every Hetzner customer and location. `spec.name` and
  `spec.location` are immutable; a name owned by someone else is `NameTaken`, and two `Bucket`
  objects for one name are a `Conflict` the oldest one wins.
- **Lifecycle rules** have only the elements Hetzner documents: expiration days, expired delete
  markers, noncurrent version expiration and incomplete multipart uploads, filtered by prefix.

## Development

How to propose a change, and how it is checked and merged: [CONTRIBUTING.md](CONTRIBUTING.md).

```console
make test               # unit tests (fake S3) + envtest (kube-apiserver + etcd)
make test-integration   # S3 client and reconciler against MinIO (Docker needed)
make lint vulncheck helm-lint
make generate manifests api-docs # after changing api/ or the +kubebuilder markers
```

Tools are pinned in the `Makefile` and installed into `./bin`. `make manifests` generates the CRD
(`config/crd/`, and `templates/crd.yaml` in the chart) and the ClusterRole, and `make api-docs` the
[API reference](docs/api.md); never edit those by hand, CI fails on drift. The envtest suite also
checks every `Bucket` under `examples/` against the CRD. The integration test uses
`cgr.dev/chainguard/minio:latest` because MinIO no longer publishes community images; set
`MINIO_IMAGE` to use another.

CI builds with the newest patch release of the Go minor in `GO_VERSION`, not with the
`go` directive of `go.mod`, which is only the minimum. govulncheck runs on every push and
also daily, so a vulnerability fixed in a new Go or dependency release turns it red
without a push; Dependabot proposes the dependency, action and base image bumps weekly.

pre-commit hooks (`pre-commit install`) run gofmt, golangci-lint, the generated-files check, helm lint
and the one-manifest-per-file rule; all of them are `language: system` and call the `Makefile` tools.
