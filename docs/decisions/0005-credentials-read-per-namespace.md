# ADR-0005: Consume credentials, read uncached and only in listed namespaces

**Status:** accepted, 2026-10-09

## Context

Hetzner has no API to create S3 credentials: they are generated by hand in the Console, one per
project, with full access to every bucket of that project. On this platform each backup project's
credential is seeded in OpenBao and materialised by External Secrets as a Secret next to the
`Bucket` objects that use it. The controller therefore reads credentials, never creates them, and
**the credential decides which Hetzner project a bucket lands in**.

How it reads them decides its RBAC. A controller-runtime client caches every kind it reads, which
for Secrets means `list` and `watch` on all of them; and a ClusterRole grant of even `get` lets the
controller read every Secret of the management cluster, which holds the credentials of the whole
platform. The `Bucket` objects, on the other hand, all live in one namespace (`backup-buckets`).

## Decision

- The Secret named in `spec.credentials` is read on every reconcile through the API server, without
  a cache. The controller needs only `get` on Secrets, never `list` or `watch`, and a rotated key is
  picked up on the next pass without a restart.
- That `get` comes from a Role and RoleBinding in each namespace of the chart value
  `rbac.secretNamespaces` (the release namespace when empty), never from the ClusterRole. There is no
  `+kubebuilder:rbac` marker for Secrets, so the generated ClusterRole cannot grow one by accident.
- A `Bucket` in any other namespace is still reconciled and stops at `CredentialsInvalid` with
  reason `SecretForbidden`, whose message names the namespace to add. The `Bucket` watch stays
  cluster-wide, so the misconfiguration is visible on the object rather than silent.
- A missing Secret is retried every `--wait-period` (1 minute by default), so one External Secrets
  writes after the `Bucket` is applied is picked up quickly. A key pair Hetzner rejects is retried
  only at the resync: a new key arrives through OpenBao, not by retrying.

Rejected: `get` on Secrets in the ClusterRole. It is simpler to install and to extend to new
namespaces, but it turns a compromise of this controller into a read of every Secret in the
management cluster.

## Consequences

- Adding a namespace that holds `Bucket` objects is a chart change, not only a new `Bucket`.
- A team bucket's credential still has to sit in one of the listed namespaces. Credentials are
  project-wide, so whoever may create Secrets or `Bucket` objects there can reach every bucket of
  that project; restrict both accordingly.
