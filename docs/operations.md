# Operations

What to look at, what the controller will and will not do for you, and the procedures that are
yours to run.

## Reading the status

`kubectl get buckets -A` shows the bucket name, location, retention mode and the `Ready` condition
with its reason. `kubectl describe bucket <name>` shows every condition and the Events:

| Condition | True means |
|---|---|
| `Ready` | the bucket exists, is owned by the credential's project and matches the spec |
| `CredentialsInvalid` | the Secret is missing, unreadable, lacks a key, or Hetzner rejects the key pair |
| `NameTaken` | the name belongs to another Hetzner project or customer |
| `ObjectLockMissing` | the bucket exists without the Object Lock the spec requests |

`status.observed` holds what the controller read from the bucket on its last pass (endpoint, Object
Lock, default retention, versioning, and lifecycle rules when managed), and
`status.observedGeneration` the spec generation it reflects. Every reason, every Event and what each
asks of you is in the [runbook](runbook.md).

## Metrics

The controller serves controller-runtime's own metrics on port 8080 (`/metrics`, plain HTTP):
`controller_runtime_reconcile_total`, `controller_runtime_reconcile_errors_total`,
`controller_runtime_reconcile_time_seconds`, `workqueue_*`, `rest_client_*` and leader election. It
publishes none of its own; the state of each bucket is in its conditions. A sustained rise in
`controller_runtime_reconcile_errors_total{controller="bucket"}` means `ProviderError`s: Hetzner is
failing or rejecting calls.

## Installing and upgrading

```console
helm upgrade --install hetzner-bucket-controller charts/hetzner-bucket-controller \
  --namespace object-storage --create-namespace \
  --set 'rbac.secretNamespaces={backup-buckets}'
```

Every value is in the [chart README](../charts/hetzner-bucket-controller/README.md). The CRD and the
ClusterRole are generated from the Go source and shipped under `templates/`, so `helm upgrade`
updates them.

The controller holds no state outside the API server and Hetzner. An upgrade replaces the pod and
the new version picks up every `Bucket` on its first pass; while it is down nothing is reconciled,
and nothing stops working either, since backup tools talk to Hetzner directly. With more than one
replica, leader election makes the others hot standbys.

`v1alpha1` makes no compatibility promise across minor versions. New fields arrive with defaults, so
an existing `Bucket` stays valid.

## Compatibility

| Component | Tested |
|---|---|
| Kubernetes | 1.37 (envtest) |
| S3 server | MinIO with Object Lock (`cgr.dev/chainguard/minio`, integration test) |
| Hetzner Object Storage | **not yet** |

The controller has not run against Hetzner yet. Everything it sends is in Hetzner's documented
subset ([ADR-0002](decisions/0002-model-only-what-hetzner-documents.md)), but one point can only be
settled on the real service: `PutBucketLifecycleConfiguration` and `PutObjectLockConfiguration`
carry a CRC32 checksum header even with `WhenRequired`, because S3 marks them as checksum-required.
If Hetzner rejects it, those `Bucket`s report `ProviderError` with Hetzner's message while creation
and the reads keep working. Until the first run succeeds, watch the first `Bucket` with a lifecycle
or a default retention reach `Ready=True`.

## Credentials

Hetzner has no API to create S3 credentials: they are generated by hand in the Hetzner Console, per
project, and give full access to every bucket of that project. **The credential decides which
project a bucket is created in.** The controller reads it from a Secret in the `Bucket`'s namespace,
keys `access-key` and `secret-key` unless `spec.credentials` names others
([ADR-0005](decisions/0005-credentials-read-per-namespace.md)).

**Rotating a key.** Create the new key in the Console, write it where the Secret comes from (OpenBao
on this platform) and let External Secrets refresh the Secret. The controller reads the Secret on
every pass, so the next one uses the new key. Before deleting the old key in the Console, force a
pass as in the [runbook](runbook.md#forcing-a-reconcile) and check that `Ready` is still `True`.

**A new namespace.** Add it to `rbac.secretNamespaces` and upgrade the release. Until then, its
`Bucket` objects report `SecretForbidden`.

The controller holds full-access credentials of every project it manages buckets in. Run it in the
management cluster only, list in `rbac.secretNamespaces` only the namespaces that hold `Bucket`
objects, and restrict who can create `Bucket` objects and Secrets in them.

## Object Lock

- **Object Lock can only be enabled when the bucket is created.** If the bucket already exists
  without it, the controller does not try to repair it: `ObjectLockMissing` turns `True`, `Ready`
  turns `False`, and a `Warning` Event says the only fix is a new bucket under another name. The rest
  of the configuration (lifecycle, versioning) is still applied.
- The presence of `spec.objectLock` is immutable, enforced by the API server.
- **`COMPLIANCE` retention cannot be shortened or lifted by anyone**, the Hetzner account owner
  included. With project-wide credentials and no IAM, that is what keeps a leaked credential from
  deleting backups. `GOVERNANCE` can be bypassed by any holder of the project's credential, so it
  protects against mistakes only.
- Changing `defaultRetention` affects only object versions written afterwards; versions already
  locked keep their retain-until date. Removing `defaultRetention` clears the bucket's default.
- Object Lock forces versioning on, permanently. Expiring an object then adds a delete marker and
  keeps the data as a noncurrent version: pair `expirationDays` with
  `noncurrentVersionExpirationDays` and a rule with `expiredObjectDeleteMarker`, or the bucket grows
  forever. Locked versions are kept until their retention lapses.
- Expiry belongs to the bucket's lifecycle, not to the producer: a backup tool that prunes old
  backups itself will fail to delete locked versions.

## Bucket names

Hetzner bucket names are global across every customer and location, and cannot be renamed:
`spec.name` and `spec.location` are immutable. A name taken by someone else is `NameTaken`; pick
another. A name you deleted is free again for your account at once, and for everyone else after 14
days. Two `Bucket` objects claiming the same name are a `Conflict`: the oldest one manages the
bucket, the others wait.

## Moving a Bucket

Deleting a `Bucket` never deletes the bucket
([ADR-0004](decisions/0004-orphan-on-delete-without-finalizer.md)), so moving one to another
namespace, another cluster or another release is: create the new `Bucket` with the same `spec.name`
and credentials, then delete the old one. While both exist the newer one reports `Conflict`; it
takes over as soon as the old one is gone, with an `Adopted` Event.

## Retiring a bucket

1. Delete the `Bucket` object. The controller stops; the bucket and its data stay.
2. Wait until no object version is under retention. With `COMPLIANCE` there is no way around this.
3. Empty the bucket, every version and delete marker included, and delete it in the Hetzner Console
   or with an S3 client.

A bucket deleted while its `Bucket` object still exists is recreated, empty, on the next pass.
